## 1. 项目定位

**一句话定位：一个运行在本地的 AI 资产管理工具，把散落在各个 AI 工具里的配置、会话历史、记忆、Skills、MCP 配置等资产统一收集、检索、备份和管理。**

### 1.1 背景与痛点

当前每个 AI 工具都自成体系地管理自己的"资产"，带来一系列问题：

- **资产散落**：MCP 配置在 A 工具里配了一份，B 工具又配一份；同一段记忆/规则要在每个工具里各写一遍。
- **会话即资产，但无处安放**：大量有价值的对话（调试过程、方案讨论、代码片段）沉在各工具的私有目录里，换工具、换机器就丢了。
- **格式私有且易变**：各家存储格式不同（JSONL / TOML / SQLite / 目录约定），且随版本升级变化，用户无从查阅更无从迁移。
- **没有备份意识**：`~/.claude`、`~/.codex`、`~/.cursor` 这些目录里积累了大量有价值数据，但没有任何版本化与备份手段。
- **记忆无法跨工具**：在这个工具里教会的偏好，到另一个工具里要重新教。

Walle 的思路：**不侵入、不替代任何 AI 工具**，在旁边做一个统一的"资产登记处 + 保险柜 + 检索器"，后期再做"同步器/迁移器"。

### 1.2 目标

1. 统一盘点本机所有 AI 工具的资产（知道有什么、在哪、什么时候变的）。
2. 提供跨工具的检索与浏览能力（尤其是历史会话全文搜索）。
3. 为所有资产提供版本化快照与备份/恢复能力。
4. （远期）支持资产的编辑写回与跨工具迁移，形成统一记忆层。

### 1.3 非目标（明确不做）

- ❌ 不做云同步、不上传任何数据 —— **纯本地优先**。
- ❌ 不替代任何 AI 工具本身（不是 IDE、不是 Agent）。
- ❌ 不修改 AI 工具的私有格式定义，只做适配（人家改格式我们跟着改）。
- ❌ Phase 4 之前对任何工具目录**只读不写**。
- ❌ 不追求一次性支持所有工具，按阶段逐个接入。
- ❌ 会话记录永远只读（写回只针对配置/记忆/Skill/MCP 等活资产）。

### 1.4 成功标准（3 个月后检验）

- 本机 4 个已确认数据源全部纳入管理，扫描幂等且不影响工具运行；
- 任意一条历史会话可通过关键词在 1 秒内检索到并完整阅读；
- 完成一次全量备份 → 模拟丢失 → 完整恢复的演练；
- 新接入一个工具的适配器工作量 ≤ 1 天（证明抽象成立）。

## 3. 概念与领域模型

### 3.1 术语表

| 术语 | 说明 |
|---|---|
| Source（数据源） | 本机上某个 AI 工具的一个实例，如"这台机器上的 Codex CLI"。有根目录、工具类型、版本。 |
| Asset（资产） | 最小可管理单元。一个 MCP 配置文件、一段记忆、一个 Skill、一条会话记录都各是一个资产。有类型、路径、内容哈希、变更时间。 |
| Snapshot（快照） | 资产在某一时刻的内容副本。扫描发现内容变化时自动留存，是备份/回滚的基础。 |
| Collection（集合） | 用户自定义的分组/标签，如"Web 项目相关记忆"、"常用 MCP"。 |
| Adapter（适配器） | 对接某个具体 AI 工具的模块，负责发现、读取（Phase 4 起还有写入）该工具的资产，并转换为统一模型。 |
| 内容仓（CAS） | Content-Addressable Storage，按内容哈希寻址的文件存储，同一内容天然去重。 |
| FTS5 | SQLite 全文检索扩展，支撑会话/记忆搜索。 |

**资产类型（kind）初始枚举：**

`config`（配置） · `session`（会话记录） · `memory`（记忆） · `skill` · `mcp`（MCP 配置） · `rule`（规则/指令文件，如 CLAUDE.md、AGENTS.md） · `prompt` · `agent` · `plugin` · `secret`（凭证类，见第 8 节） · `other`

### 3.2 数据模型草案（SQLite）

```sql
-- 数据源：本机一个 AI 工具实例
CREATE TABLE source (
  id INTEGER PRIMARY KEY,
  tool TEXT NOT NULL,            -- zcode / codex / cursor / ...
  display_name TEXT,
  root_path TEXT NOT NULL,
  tool_version TEXT,
  last_scanned_at TEXT
);

-- 资产
CREATE TABLE asset (
  id INTEGER PRIMARY KEY,
  source_id INTEGER NOT NULL REFERENCES source(id),
  kind TEXT NOT NULL,
  name TEXT,
  path TEXT NOT NULL,            -- 相对 source 根目录
  raw_format TEXT,               -- jsonl / toml / sqlite / markdown / dir
  content_hash TEXT,             -- sha256，用于去重与变更检测
  size INTEGER,
  mtime TEXT,
  sensitive INTEGER DEFAULT 0,   -- 1 = 凭证/秘密类，展示脱敏、FTS 排除（见第 8 节）
  first_seen_at TEXT,
  last_seen_at TEXT,
  status TEXT DEFAULT 'active'   -- active / missing / deleted
);

-- 会话扩展元数据（kind = 'session' 时）
CREATE TABLE session_meta (
  asset_id INTEGER PRIMARY KEY REFERENCES asset(id),
  started_at TEXT, title TEXT, model TEXT,
  message_count INTEGER, project_path TEXT,
  token_in INTEGER, token_out INTEGER
);

-- 快照：内容历史
CREATE TABLE snapshot (
  id INTEGER PRIMARY KEY,
  asset_id INTEGER NOT NULL REFERENCES asset(id),
  captured_at TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  size INTEGER,
  storage_path TEXT NOT NULL     -- 内容仓中的位置
);

-- 用户自定义集合
CREATE TABLE collection (id INTEGER PRIMARY KEY, name TEXT UNIQUE, note TEXT);
CREATE TABLE collection_item (
  collection_id INTEGER REFERENCES collection(id),
  asset_id INTEGER REFERENCES asset(id),
  PRIMARY KEY (collection_id, asset_id)
);

-- 全文索引（P2 落地，contentless 模式，正文存内容仓）
CREATE VIRTUAL TABLE asset_fts USING fts5(name, body, content='');

-- 常用索引
CREATE INDEX idx_asset_source_kind ON asset(source_id, kind);
CREATE INDEX idx_asset_hash ON asset(content_hash);
CREATE INDEX idx_snapshot_asset ON snapshot(asset_id, captured_at DESC);
```

> Schema 演进使用 `PRAGMA user_version` 做版本化迁移，禁止启动时盲目 `CREATE TABLE`。

## 4. 总体架构

```
┌───────────────────────────────────────────────────┐
│                 界面层（分阶段演进）                │
│      CLI (P1)  →  本地 Web UI (P2)  →  桌面应用(P5) │
├───────────────────────────────────────────────────┤
│                       服务层                       │
│   扫描调度 · 全文检索 · 快照/备份 · 同步引擎(P4)     │
├───────────────────────────────────────────────────┤
│                 适配器层（每工具一个）               │
│    zcode │ codex │ cursor │ opencode │ workbuddy │ vscode │ …  │
│    统一接口: discover() / read() / [write()(P4)]   │
├───────────────────────────────────────────────────┤
│                       存储层                       │
│    SQLite（元数据 + 全文索引） +  内容仓（CAS 文件） │
└───────────────────────────────────────────────────┘
```

### 4.1 关键设计决策

1. **元数据与内容分离**：SQLite 只存索引和元数据；资产内容按哈希存入内容寻址文件仓，同一内容天然去重，也直接支撑快照与备份。
2. **适配器模式**：每接入一个新工具只需写一个 adapter，上层（CLI/UI/检索）完全不感知工具差异。成功标准见 1.4（≤1 天接入新工具）。
3. **只读优先**：扫描器对工具目录以只读方式访问（SQLite 用 `mode=ro` 或副本，JSONL 直接读），任何写能力都要到 Phase 4 且带强制快照。
4. **能力声明而非能力探测**：适配器通过 `capabilities.write` 显式声明是否支持写，上层据此硬性拦截写请求，杜绝"误调用未实现的写路径"。

### 4.2 Walle 自身数据布局

```
~/.walle/
├── walle.db          # SQLite 元数据 + FTS 索引
├── objects/          # 内容仓（CAS）：按哈希前 2 位分桶，如 ab/abcdef…
├── exports/          # 导出归档默认输出目录
└── config.json       # walle 自身配置（启用哪些源、忽略规则等）
```

### 4.3 适配器接口规范（v1 草案）

```ts
/** 适配器统一接口。P1-P3 所有适配器 write 均为不可用。 */
interface Adapter {
  id: string;                     // 'codex' | 'zcode' | 'cursor' | ...
  displayName: string;

  /** 探测本机是否存在该工具的数据目录，返回根路径；不存在返回 null */
  detect(): string | null;

  /** 枚举该源下全部资产（只读、流式，大目录不一次载入内存） */
  discover(root: string): AsyncIterable<RawAsset>;

  /** 读取单个资产，返回统一内容对象 */
  read(asset: RawAsset): Promise<AssetContent>;

  /** 将结构化资产（会话/记忆）解析为统一模型；非结构化资产可不实现 */
  parse?(content: AssetContent): ParsedSession[] | ParsedMemory[];

  /** P4 起按工具逐步实现；实现方必须自带：前置快照 + 原子写 + 冲突检测 */
  write?(asset: RawAsset, content: AssetContent): Promise<void>;

  capabilities: { read: true; write: boolean };
}

interface RawAsset {
  kind: AssetKind;
  path: string;                   // 相对 root
  rawFormat: 'jsonl' | 'toml' | 'json' | 'sqlite' | 'markdown' | 'dir';
  size: number;
  mtime: string;
  sensitive?: boolean;            // 凭证类资产由适配器负责标记
}
```

### 4.4 CLI 命令面（随阶段演进）

```
walle scan  [--source codex]      # 扫描（默认全源，mtime+hash 增量）      [P1]
walle list  [--kind session] [--source zcode] [--json]                     [P1]
walle show  <asset-id>            # 查看资产详情与内容                     [P1]
walle search "关键词" [--kind session]   # 全文搜索                        [P2]
walle serve  [--port 4173]        # 启动本地 Web UI                        [P2]
walle snapshot [asset-id]         # 手动/查看快照                          [P3]
walle backup  [-o archive.zip]    # 全量导出归档                           [P3]
walle restore <archive.zip>       # 从归档恢复                             [P3]
walle diff <asset-id> [--snap a:b]# 版本对比                               [P3]
walle push   <asset-id> --to <source>   # 资产下发/迁移                    [P4]
```

**实测发现的两个重要事实：**

1. `~/.codex/auth.json` 是真实凭证文件，扫描器必然会碰到 —— 敏感数据处理策略见第 8 节，**不可入库明文、不可进全文索引**。
2. `~/.codex` 下存在 `config.toml.pebrel-bak`、`hooks.pebrel-managed.json`、`cc-switch-model-catalog.json`，说明本机有第三方管理工具（pebrel / cc-switch）在**并发修改**这些配置。P4 写回时的冲突检测必须把"第三方工具同时改文件"当作常态而非边角案例。

**Phase 0 调研模板**（每个工具一份）：**资产清单 → 精确路径 → 文件格式 → 读取方式与坑（文件锁/大文件/编码）→ 变更频率 → 是否可写回及风险**。

**待评估接入**：Claude Code（`~/.claude`）、Gemini CLI、Windsurf、Cline、Continue、Chatbox/Cherry Studio 等桌面客户端。

## 6. 技术选型（已定案，见 ADR-001）

**TypeScript monorepo —— Node.js ≥ 22.13 内置 `node:sqlite`（零原生依赖）+ 本地 Web UI（Vite + Vue 3 + Naive UI）**，远期用 Tauri 打包成桌面应用。

- **语言/运行时**：TypeScript 5 + Node ESM（NodeNext）；npm workspaces 单包多模块（core / adapters / cli / ui）；
- **SQLite**：Node 22 内置 `node:sqlite`（FTS5 可用），**不引入 better-sqlite3**——CLI 运行时零原生依赖，若未来 API 破坏性变更只需改 `store.ts` 一处（ADR-001 D2）；
- **CLI**：`parseArgs` 自研分发，运行时零 npm 依赖；UI 构建产物由 CLI 静态托管（`walle serve`）；
- **UI**：初版无框架单文件（P2）→ Vite + Vue 3 + TS 工程化（UI-1）→ Naive UI + Apple 风格主题（UI-2，苹果蓝 #0071e3 / SF 字体栈 / 毛玻璃侧栏）；
- 初期"better-sqlite3 + React"的推荐已被 ADR-001 取代，决策依据见 `docs/adr/ADR-001-tech-stack.md`。

## 7. 分阶段开发计划

> **阶段原则**：① 每个阶段结束时产品独立可用；② 只读优先，写能力最后做；③ 每阶段明确"不做什么"，范围外一律记入 backlog 不动手；④ 前一阶段的交付物是后一阶段的地基，但阶段间允许回补设计。

### 里程碑总览

| 阶段 | 主题 | 核心交付 | 覆盖场景 | 预估 | 状态 |
|---|---|---|---|---|---|
| P0 | 调研定案 | 数据源报告、ADR、仓库骨架 | — | 0.5~1 周 | ✅ 2026-09-30 |
| P1 | 只读扫描 CLI | `walle scan / list / show` | S5 | 1~2 周 | ✅ 2026-09-30 |
| P2 | 浏览与检索 | Web UI + 全文搜索 | S1 | 2~3 周 | ✅ 2026-09-30 |
| P3 | 快照与备份 | 备份/恢复/对比 | S2 | 1~2 周 | ✅ 2026-09-30 |
| P4 | 写回与迁移 | 编辑、下发、跨工具迁移 | S3 | 2~4 周（可拆期） | ✅ 2026-10-01 |
| P5 | 智能化与生态 | 统一记忆层、桌面化、插件机制 | S4 | 远期 | 🚧 进行中（详见下） |

### Phase 0 —— 调研与定案

| 项 | 内容 |
|---|---|

## 8. 敏感数据与安全策略

扫描器必然接触到凭证与隐私数据（已实测 `~/.codex/auth.json` 存在），策略如下：

**资产分级：**

| 级别 | 判定 | 示例 |
|---|---|---|
| secret | 凭证/密钥文件或字段 | `auth.json`、config 中的 API key、mcp.json 中的 Authorization header |
| private | 会话、记忆等个人数据 | 全部 session/memory 资产 |
| normal | 其余 | 公开 Skill、通用配置模板 |

**处理规则：**

1. **入库**：secret 资产内容仍入内容仓（备份需要），但 `asset.sensitive=1`；仓内 secret 可选加密（AES-256 + 主密码，P3 起提供）。
2. **展示**：secret 资产在 CLI/UI 中默认脱敏（仅显示前后 4 字符），明文查看需显式操作。
3. **索引**：secret 资产**永不进入 FTS 全文索引**。
4. **导出**：`walle backup` 默认排除 secret，需 `--include-secrets` 显式包含。
5. **日志**：任何日志/错误上报不打印完整 secret（统一走脱敏工具函数）。
6. **本地承诺**：无遥测、无云端上报，所有数据留在 `~/.walle/`。

## 10. 工程实践

- **测试固件（fixtures）**：每个工具准备一份**脱敏后的样本数据目录**（含典型格式与边界情况），适配器单测全部跑在固件上，不依赖真机数据。工具升级格式时，更新固件即形成回归用例。
- **真机冒烟**：CI 之外保留一个本机冒烟脚本（scan 两次验证幂等 + show 抽查），发布前手跑。
- **Schema 迁移**：`PRAGMA user_version` 版本化，迁移脚本只增不改。
- **版本策略**：语义化版本（0.x 阶段以阶段号为大版本：0.1.x=P1，0.2.x=P2 …）。
- **CI**：lint + 单元测试 + 固件回归（GitHub Actions）。
- **文档节奏**：每阶段结束回写本文档状态与修订记录；数据源调研报告随工具版本升级持续维护。
